# 기능 하나를 완성하는 기준

새 프로젝트에서는 이 문서를 `FEATURE-WORKFLOW.md`로 제공합니다. React 단독이면 Mock까지,
Nest 단독이면 API까지, 모노레포면 양쪽을 같은 계약으로 구현합니다.

## 1. 요청을 관찰 가능한 동작으로 바꾸기

사용자, 시작 상태, 행동, 성공 결과, 실패 결과를 먼저 적습니다. 예를 들어 작업 관리라면
“로그인한 사용자가 작업을 등록하면 자신의 목록에서 바로 확인하고, 새로고침해도 유지된다”입니다.
대상 사용자와 필드가 결정되지 않았다면 해당 결정을 요구사항에 남깁니다.

웹의 `docs/requirements.md`에 다음 번호의 요구사항을 추가합니다. 기존 REQ-1부터 REQ-6은
인증과 앱 틀입니다. 중복 번호를 쓰거나 기존 요구사항을 지워 검증을 통과시키지 않습니다.

```markdown
## REQ-7 작업 등록

- 로그인한 사용자만 제목을 입력해 등록할 수 있다.
- 제목은 공백 제거 후 1~100자이며 서버도 같은 규칙으로 검사한다.
- 실패하면 입력값을 보존하고 해당 필드 또는 화면에서 원인과 재시도 방법을 알린다.
- 등록한 작업은 본인의 목록에서만 보인다.
```

## 2. 데이터와 권한을 먼저 정하기

| 항목 | 정할 내용 |
|---|---|
| 소유권 | 개인 데이터인지, 조직 공유인지, 누가 읽고 변경할 수 있는지 |
| 필드 | 타입, 필수 여부, 길이, 기본값, 수정 가능한 값 |
| 식별자 | 서버가 생성하는 ID와 외부 노출 가능 여부 |
| 목록 | 검색, 정렬, 페이지 크기와 최대값, 필터, 빈 결과 |
| 변경 | 중복 제출, 이미 삭제된 항목, 충돌 시 응답 |
| 보존 | 삭제 방식, 관련 데이터 처리, 게스트 데이터 수명 |

모노레포는 `packages/shared/src/<resource>.ts`에 Zod 스키마와 타입을 정의하고 `index.ts`에서
내보냅니다. React 단독은 `src/entities/<리소스>/api.ts`, Nest 단독은 `src/contracts/`가 계약의 위치입니다.

API 오류는 `{ message, fields? }`, 목록 응답은 `{ items, total, page, pageSize }` 형태를 기준으로
설계합니다. 화면의 비활성 버튼만으로 권한을 처리하지 않습니다. 서버의 조회·수정·삭제 쿼리가
현재 사용자 또는 조직 범위를 항상 포함해야 합니다. 기존 스키마에는 조직과 역할이 없습니다.

## 3. API와 Mock을 함께 구현하기

API는 테이블과 마이그레이션, 서비스, 컨트롤러, 모듈 순서로 추가합니다. `AuthGuard`를 연결하고
`parse()`로 입력을 검증합니다. 실제 사용자 데이터가 필요한 테스트는 메모리 DB로 격리합니다.

Mock은 같은 경로·요청·응답·필드 오류를 구현합니다. `src/mocks/browser.ts`에 핸들러를 등록하고
`src/mocks/db.ts`에 필요한 테이블과 재현 가능한 시드를 넣습니다. 성공 응답만 흉내 내지 말고
검증 오류, 미인증, 다른 사용자의 데이터 요청, 없는 ID도 같은 방식으로 응답합니다.

게스트는 매번 별도 ID를 받습니다. `u_guest` 같은 상수를 권한이나 소유자 판정에 사용하지 않습니다.
소셜 계정도 이메일만으로 기존 계정에 연결하지 않습니다. 명시적인 계정 연결은 별도 요구사항입니다.

## 4. 화면의 전체 흐름을 마무리하기

라우트 파일에 `// REQ-7 ...`를 적고 사이드바에 연결합니다. 데이터 조회는 Query와 라우트 로더를
사용하고, 변경 성공 후 관련 목록·상세 캐시를 갱신합니다. 기본 제공 입력과 UI 컴포넌트를 사용합니다.

- 첫 로딩, 검색 중, 데이터 없음, 검색 결과 없음, 서버 오류를 구분합니다.
- 폼은 검증 오류, 전송 중 중복 클릭, 실패 후 재시도와 입력 보존을 확인합니다.
- 변경 취소와 삭제는 사용자가 결과를 예상하고 되돌아갈 수 있게 설계합니다.
- 키보드 포커스, 레이블, 모바일 폭, 긴 한국어·긴 숫자를 확인합니다.
- 날짜·금액·전화번호·사업자번호는 공통 함수를 사용합니다. 사업자번호 체크섬은 실존 사업자 조회가 아닙니다.

## 5. 완료를 증명하기

| 검증 | 확인하는 동작 |
|---|---|
| 단위 테스트 | 경계값과 도메인 계산·검증 규칙 |
| API 계약 테스트 | 생성·조회·변경·삭제와 필드 오류, 사용자 간 접근 거부 |
| 브라우저 E2E | 사용자가 화면에서 끝까지 수행하는 시나리오와 새로고침 후 상태 |
| 요구사항 검사 | REQ 번호가 문서·라우트·E2E에 연결됐는지 |

E2E 이름은 `REQ-7 ...`로 시작합니다. 추적 검사는 링크의 존재를 확인하므로, 테스트 본문에서 실제
사용자 결과를 검증해야 합니다. 모노레포의 `pnpm verify`는 공유 패키지와 API, 실서버 웹,
Mock 웹을 검증합니다. 계정·데이터가 실행 간 섞이지 않도록 테스트 전용 서버를 사용합니다.

기능 완료 보고에는 달라진 사용자 동작, 실행한 검증, 남은 제한을 적습니다. 검증이 실패했다면
성공으로 기록하거나 검사를 약하게 바꾸지 않습니다.

## 6. 운영에 연결하기

웹의 `VITE_API_URL`은 빌드 시 반영됩니다. 모노레포의 개발 프록시는 운영에 포함되지 않으므로
배포 환경에서 `/api`를 API 서버로 라우팅하고, 나머지는 SPA로 제공해야 합니다.

API는 영구 PostgreSQL 주소, 실제 웹·API URL, OAuth 콜백 URL을 설정하고 공개 환경에서는
`DEMO=false`, `ALLOW_GUEST=false`를 명시합니다. API 시작 시 마이그레이션이 적용됩니다.
백업·복구, 로그 보존, 요청 제한, 이메일 인증·비밀번호 재설정, 역할·조직 권한은 배포할 제품의
범위에 맞춰 구현하고 검증합니다. 현재 템플릿이 제공하는 기능으로 간주하지 않습니다.
